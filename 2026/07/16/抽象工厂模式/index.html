抽象工厂模式

发表于2026-07-16|更新于2026-07-16|设计模式
|浏览量:

如果说昨天的工厂方法是针对单个产品（比如只生产卡车），那么今天的抽象工厂就是针对产品族（比如生产一整套豪华汽车组件，包括豪华车轮、豪华方向盘）。

Day 3：抽象工厂模式 (Abstract Factory Pattern)

1. 它是怎么来的？

想象一下，你正在开发一款跨平台的 UI 工具包（支持 Windows 和 Mac）。
UI 组件有很多种：按钮（Button）、复选框（Checkbox）、文本框（TextField）。

如果你用昨天的工厂方法，你得写一个 ButtonFactory、一个 CheckboxFactory。
但这里有一个致命的隐患：你必须确保 Windows 系统上创建的按钮和复选框都是 Windows 风格的，绝对不能在 Mac 系统里误用了一个 Windows 风格的按钮。

这就引入了“产品族”的概念。Windows 的按钮和 Windows 的复选框属于同一个产品族；Mac 的按钮和 Mac 的复选框属于另一个产品族。

抽象工厂模式就是为了解决“一系列相互依赖的产品的创建问题”而诞生的：提供一个接口，用于创建相关或依赖对象的家族，而不需要明确指定具体类。

2. 适用场景

  • 产品族群：系统需要由多个相关联的产品对象组成，且它们必须配套使用。
  • 跨平台/多主题切换：如支持多种操作系统界面（Windows/macOS/Linux）、更换软件皮肤主题（暗黑模式/明亮模式）。
  • 解耦依赖：客户端不应该依赖具体产品的创建细节，只通过高度抽象的接口与产品族交互。

3. 优缺点分析

优点 缺点
保证产品族一致性：强制同一个工厂生产出来的产品都在一起配套使用，绝不会出现“混搭”Bug。 扩展“新产品”极难（违反开闭原则）：如果产品族里要新增一个组件（比如加一个下拉框 Dropdown），你需要修改抽象工厂以及所有的具体工厂类。
高解耦：客户端代码与具体平台、具体产品的实现完全隔离。 代码结构复杂：抽象层级非常深，类的数量会成倍增加。
符合单一职责原则：将特定产品族的创建代码集中到一个地方。

在现代后端架构中，抽象工厂常用于多数据库/多存储源的切换。
假设你的应用需要同时支持关系型数据库（MySQL）和 NoSQL 数据库（MongoDB），它们各自都有一套独立的“连接器”和“查询器”。

区分总结：三大工厂到底有什么区别？

  • 简单工厂（不是设计模式）：一个工厂类负责根据参数创建所有产品。新增产品时要改动工厂内的 if-else。
  • 工厂方法模式：一个工厂只对应一种产品（卡车工厂造卡车，轮船工厂造轮船）。
  • 抽象工厂模式：一个工厂负责生产一整套关联的产品族（Windows工厂既造Win按钮，又造Win复选框）。
